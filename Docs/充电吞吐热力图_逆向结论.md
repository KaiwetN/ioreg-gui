# AirPods 充电吞吐值与热力图分档

分析日期：2026-10-09。分析对象：本机缓存的 AirPods Pro 2 9.1.42 / STFW 镜像及 a2699 TMAP；使用 Ghidra 和 Capstone 静态分析。

## 结论

`acc_charge_throughput_soc_temp_matrix_ma_per_min_*_*` 记录**耳机电池在对应电量计 SOC 与电池温度区间内，累计充入的电荷量**。名称里的 `ma_per_min` 容易误读：实际数值单位是 **mA·min（毫安分钟）**，不是 mA/min。

换算：`累计充入电荷 (mAh) = 原值 / 60`。

左耳的格子原值 **144,027**（旧图缩写为 144k）对应 **2,400.45 mAh**，约占该耳已上报总量 **18.54%**。该格实际范围为 **20 ≤ SOC < 40%**、**27 ≤ 电池温度 < 35°C**。这是跨多次充电的累计量，可以远大于耳机单次满充的几十 mAh；它不是当前容量、充电次数、USB 输入电流或能量 Wh。

本机该快照：左耳全部格子合计 776,886 mA·min = **12,948.10 mAh**；右耳 853,156 mA·min = **14,219.27 mAh**。这两个数是已上报矩阵的合计，不应再乘 analyticsd 的事件计数。

## 指令证据

STFW 大小 511,136 字节，加载基址 **0x08001800**。基址依据向量表、启动函数和字符串指针共同核验。

SHA-256：`13486d90ee8c46cb0f0dc3c4ad865ea5fdb5b9cce2dfb5fe6aa48eec1fab94be`。

| 位置 | 证据 | 含义 |
|---|---|---|
| `0x08052310` | 健康数据更新函数 | 使用电池样本中的 SOC、温度、电流与时间 |
| `0x080527ce`–`0x08052808` | 样本 `+0x12` 读取有符号电池电流，`+0x06` 读取 SOC，`+0x08` 读取温度；分别查 9 档、5 档 | 热力图依据电池侧样本分档 |
| `0x080526c8` | 浮点常量 `1000.0` | 毫秒到秒的时间比例 |
| `0x08052810`–`0x0805282a` | 时间差 / 1000，+0.5 后转整数 | 积分使用四舍五入的经过秒数 |
| `0x08053d88` | 电流状态分类：大于 0.1 时进入充电状态 2；近零为闲置、负电流为放电 | 吞吐矩阵只在充电分支累加 |
| `0x080528b2`–`0x080528da` | `vmul.f32` 将电池电流与秒数相乘，转整数后累加至矩阵 `+0x21c` | RAM 中累计的是 mA·s |
| `0x08052954`–`0x08052990` | 选取吞吐矩阵，`udiv ... #0x3c`（60），传给 `0x080572f0`，目标 NVM 偏移 `+0x275` | 持久化原值 = mA·s / 60 = mA·min |
| `0x080572f0` | 存储为 24 位小端整数，超过上限饱和 | 原值有量化及上限，不是无限精度积分 |
| `0x080521dc`，尤其 `0x08052272`–`0x0805228c` | 启动时把持久化吞吐值读取后乘 60，恢复 RAM 矩阵 | 反向确认“存储除 60 / 恢复乘 60”配对 |
| `0x08040b40`，尤其 `0x08040d7a`–`0x08040d8a` | NVM `+0x275` 的 3 字节原值展开为事件内 4 字节整数，未再缩放 | TMAP / analyticsd 中仍然是 mA·min |
| `0x080792f4` | 调试字符串 `Acc chg throughput %s(ma_per_min):` | 对应同一吞吐矩阵 |
| `0x0807b775` | 调试字符串 `SOCTEMP_HMAP_timeAt_%d:%ds, Ibatt:%d` | 同一积分路径打印秒数及电池电流 |

TMAP 的事件为 `com.apple.Bluetooth.AccessoryBatteryHealthV4Metric`，含 `bud_side`；字段索引 213（从 0 开始）是矩阵 `_0_0`，类型 `UnsignedInteger`、长度 4。analyticsd 配置表达式仅为 `[字段名, ":getEventField"]`，没有额外缩放。这也确认了矩阵应按左右耳展示。

关键流程（省略缓存地址和调试开关）：

```text
seconds = round((sample.timestamp_ms - previous.timestamp_ms) / 1000)
soc_bin = lookup(sample.SOC, SOC_thresholds)
temp_bin = lookup(sample.battery_temperature_C, temperature_thresholds)
if current_state(sample.battery_current_mA) == charging:
    accumulator_mA_seconds[soc_bin][temp_bin] += truncate(current_mA * seconds)
    stored_value[soc_bin][temp_bin] = floor(accumulator_mA_seconds / 60)
reported_value = stored_value           # 原值展开，无二次缩放
display_mAh = reported_value / 60
```

## 真实分档

初始化函数 `0x080521dc` 把 SOC 表 `0x0806e84c` 绑定到配置 `+0x0c`，温度表 `0x0806e85e` 绑定到 `+0x10`。更新函数使用这两个配置项查表，查表函数为 `0x08056fa2`。因此不是凭相邻数据猜测边界。

SOC 下限数组：`[0, 10, 20, 40, 60, 80, 85, 90, 95]`。

| 原始行索引 | SOC 区间 |
|---|---|
| 0 | 0–10% |
| 1 | 10–20% |
| 2 | 20–40% |
| 3 | 40–60% |
| 4 | 60–80% |
| 5 | 80–85% |
| 6 | 85–90% |
| 7 | 90–95% |
| 8 | 95–100% |

温度下限数组：`[0, 20, 27, 35, 42]`。

| 原始列索引 | 电池温度区间 |
|---|---|
| 0 | <20°C，包括负温度 |
| 1 | 20–27°C |
| 2 | 27–35°C |
| 3 | 35–42°C |
| 4 | ≥42°C |

区间下限包含、上限不含；末端包含 100% SOC。9.0.348 镜像也能检出相同的两张分档表。本次查看器对已核验的 Pro 2 / `sw_version=9503393` 使用这些范围，其他型号或版本仍保留档位编号，防止误套。

## 精度与解释边界

固件按样本电流和四舍五入的经过秒数积分，并截断、压缩到整数。显示 2,400.45 mAh 表示对已上报原值的数学换算，不代表实验室级测量精度。24 位饱和或设备侧重置也会影响长期累计。颜色表示累计充入电荷的分布，不能独立用于判断老化程度。
